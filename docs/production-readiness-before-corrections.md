# Kikwetu Eggs production-readiness audit

Audit date: 9 November 2026. **Release recommendation: NO-GO for the complete requested release.** Passing tests confirm the covered scenarios, but the additional audit probes found financial and authorization defects. This report supersedes any implication in the earlier implementation notes that passing local tests alone establishes production readiness.

Only local code, public provider documentation, disposable SQLite databases and mocked Daraja responses were used. No Render/Netlify account was accessed, no production migration ran, no real payment was initiated, and no live data was changed. Application code and dependency versions were not changed during this audit. Added files are the audit probe, its evidence, this report and the deployment checklist.

Additional operational risks that need remediation or explicit release acceptance:

- **Timeout budget:** `_json_request` allows 20 seconds per call; OAuth plus STK/query can approach 40 seconds while locks remain held. The documented Gunicorn start command does not override the installed default 30-second worker timeout. Establish an end-to-end timeout budget and durable recovery; increasing the worker timeout alone does not solve lost-payment tracking. [Gunicorn settings](https://gunicorn.org/reference/settings/).
- **Production config fails open:** missing `DATABASE_URL` silently uses a local SQLite file; missing `SECRET_KEY` creates a new random key per application instance. On Render these can mean unexpected storage or inconsistent/logout-prone sessions. Validate required production configuration before starting. Confirm the existing service uses PostgreSQL and one stable secret without exposing their values.
- **Scalability:** notification polling reads all orders and completed payment attempts and attempts inserts for every historical event every 30 seconds per admin. Financial reports load all orders/payments in Python, and expense history is unpaginated. Benchmark realistic data volumes, replace repeated historical reconciliation with incremental generation, and inspect query plans before increasing usage.
- **Additional index/relationship decisions:** missing administrator foreign keys and missing lookup/order indexes are described below. They are not supplied automatically by the migration.
- **Notification history UI:** opening older pages is temporary; the next poll replaces the loaded history with the first page. Preserve pagination while refreshing counts. Historical cancellation notifications derive time from mutable `orders.updated_at`, not an immutable cancellation timestamp.
- **Rate limits:** the existing memory limiter resets on restart and is per process/worker, even on one Render instance. A shared store is needed for consistent limits across multiple workers or instances. The callback route has no dedicated abuse limit; any limit must allow legitimate provider retries.
- **Health/runtime checks:** no dedicated database-readiness endpoint or runtime version pins were found. The supplied start command also runs `init_db.py` on each boot, including optional admin-create/reset behavior. Review this separately from the additive migration.

## Migration, tables and data preservation

The exact current migration contains only four `CREATE TABLE IF NOT EXISTS` statements and one `CREATE INDEX IF NOT EXISTS` statement. It does not alter, delete, update, truncate or rebuild existing orders, customers, products, order items, payments, M-Pesa transactions or admins. There are **no new columns added to existing business tables**. The snapshot probe included real-shaped rows in all seven tables and matched them after both runs.

PostgreSQL compatibility is **reviewed, not executed**: BIGSERIAL/BIGINT identities and relationships, NUMERIC precision, DATE, TIMESTAMPTZ, primary/unique/check constraints, ON CONFLICT, RETURNING and row locking are PostgreSQL constructs. The psycopg adapter executes statements on a non-autocommit connection and commits after the script; a PostgreSQL failure should roll back that transaction. Confirm this on the production PostgreSQL version and role. SQLite `executescript` does not provide the same all-or-nothing guarantee here; an interrupted SQLite migration can leave a partial but normally rerunnable schema.

`IF NOT EXISTS` is not schema validation: PostgreSQL explicitly states that an existing relation need not match the requested definition. No migration ledger, schema-version validation, advisory migration lock, lock timeout or statement timeout is present. The migration also assumes the existing `orders` table has the required primary key and that the intended schema/search path and DDL privileges are correct. [PostgreSQL CREATE TABLE documentation](https://www.postgresql.org/docs/18/sql-createtable.html).

SQLite uses INTEGER identity keys and TEXT timestamps for the same structures. Its NUMERIC affinity does not enforce PostgreSQL numeric precision/scale. Decimal server arithmetic and tested bounds help, but PostgreSQL numeric behavior still needs engine testing. Soft deletion retains expense rows; audit snapshots retain the previous state for updates/deletions. Audit writes and expense changes share a transaction. Idempotency keys are globally unique and retained after deletion.

Existing callback receipt and checkout IDs already have unique constraints. `idx_mpesa_transactions_order_status` is **not** a unique partial index enforcing one pending attempt per order. The new migration does not add such a constraint or repair legacy duplicate attempts; inspect them on staging before deciding on a safe incremental constraint.

## M-Pesa review: protections that are present

- Customer-only initiation/status endpoints check order/transaction ownership and reject cancelled or already-paid orders.
- The frontend does not mark a payment paid from STK initiation. Initiation stores pending state; success requires backend verification.
- The callback is public by design. It checks provider STK query result using server-side OAuth, then compares success amount, merchant request ID, phone and nonempty receipt. This is independent status verification, **not cryptographic authentication of the incoming callback or independent verification of its receipt string**.
- SQLite write serialization and PostgreSQL order/transaction row locks are present on initiation and callback paths. Same-attempt terminal duplicates return without reapplying state; receipt/checkout uniqueness supplies additional protection.
- Successful late receipts for cancelled/already-paid orders are retained with reconciliation notifications. Paid/partially-paid customer cancellation is rejected and cancelled orders are not deleted.
- No M-Pesa credential use was found in frontend source. The service's error handling omits provider credential bodies from logs.
- Existing tests cover successful/failed callbacks, serial duplicates, mismatched provider result, invalid amount, provider-query outage and late cancelled-order receipts. They **do not** prove concurrent PostgreSQL behavior, durable recovery or real Daraja contract behavior. Official Daraja query documentation was not retrievable in this audit; provider retry/receipt authenticity assumptions remain unverified.

## Timezone and report review

Verified locally: PostgreSQL connections request UTC; PostgreSQL schema timestamps are TIMESTAMPTZ; SQLite CURRENT_TIMESTAMP is interpreted as UTC. `business_time.py` uses aware UTC and fixed UTC+03:00 EAT, suitable for current Nairobi business dates. Frontend formatting explicitly uses `Africa/Nairobi` and handles both legacy naive UTC strings and existing offsets without appending an extra `Z`. Weekly boundaries are Monday–Sunday, monthly boundaries include leap years, and custom end dates are inclusive. Existing tests cover Nairobi midnight, year/week boundaries, leap-month boundaries and equal display of naive/offset-aware instants. CSV timestamps and legacy report date filters use Nairobi conversion.

Unverified/incorrect aspects: B7's receipt time; historical naive values may already have been stored as local time by another importer and cannot safely be assumed corrected by this change; cancellation time has no immutable column; partial and refunded cash calculations are inconsistent (B2/B3). Legacy dashboard/report endpoints still use whole-order flags/creation-date definitions and can disagree with the new financial summary. The new Paid Orders card means receipts for valid orders, including partial receipts, not strictly the total value of fully paid orders. The UI states that definition, but business approval is required because it differs from the original full-paid-order definition. Unpaid Orders is a cohort of orders created during the period, not all receivables outstanding at period end.

## Authentication and environment documentation

Blueprint `before_request` guards protect expense, notification and report routes. All nine new endpoint/method combinations returned 401 without a session and 403 with a customer session. OPTIONS returns 204 before authorization for CORS preflight and does not execute business actions. Signed sessions and exact-origin credentialed CORS are configured; the revoked-admin gap B6 must still be fixed. Real cross-site cookies, custom domains and browser third-party-cookie restrictions need staging tests; local mocked requests do not exercise Netlify-to-Render cookie policy.

The names of all current application-owned environment variables exist in `backend/.env.example`, `frontend/.env.example` and/or README. However, README lacks a complete Netlify configuration and wrongly says there is a Vite development proxy: `vite.config.js` has no proxy and the frontend uses `VITE_API_URL`. Direct Python migration/init commands do not load `.env` themselves. Render must inject variables, or an operator must export them explicitly. No secret values were read or copied into this report. The [deployment checklist](deployment-checklist.md) provides the complete variable matrix and corrected commands.

## Dependency findings

The production-only registry audit reports two moderate package entries (`react-router` and `react-router-dom`) arising from React Router advisories. It suggests a major-version upgrade to 7.18.5; no upgrade was applied. Review compatibility and add navigation tests before upgrading rather than using `npm audit fix --force` blindly. [Saved audit output](production-readiness-npm-audit.json).

The SSR hydration advisory explicitly excludes Declarative Mode, which this application uses with BrowserRouter/Routes; it is not currently an SSR deployment. The open-redirect advisory concerns attacker-controlled navigation destinations; the inspected application routes use fixed internal paths or numeric IDs, and this audit did not demonstrate an exploitable destination. Record this applicability assessment or upgrade to a tested patched release before sign-off. [Open-redirect advisory](https://github.com/advisories/GHSA-wrjc-x8rr-h8h6), [SSR advisory](https://github.com/advisories/GHSA-337j-9hxr-rhxg).

Only production npm dependencies were security-scanned. No comprehensive Python/development-tool vulnerability scan was performed. `pip check` must not be described as such a scan.
